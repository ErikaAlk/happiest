Happiest ships a few pieces, and **how updates work depends on how you installed each one**.

This page is the “source of truth” for:

- which pieces update automatically vs manually
- what commands to run for each install method
- how the stable channel maps to rolling release tags
- where the web UI comes from in self-hosted deployments

## Update channels

Happiest publishes one channel, `stable`, as GitHub Releases on `ErikaAlk/happiest`. There are no preview or dev releases.

Under the hood, the channel is implemented using **rolling release tags**: `cli-stable`, `server-stable` and `ui-desktop-stable`. Each tag is updated to point at the newest version of its piece. Every release also keeps a versioned tag (`cli-v<version>`, `server-v<version>`, `ui-desktop-v<version>`) for pinning an exact version. Versions start at `0.1.0`.

The CLI and the relay server are published for Windows x64, Linux x64 and Linux arm64. The desktop app is published for Windows x64 and Linux x64. There are no macOS builds, no npm packages, no Homebrew formula and no Docker images, and hstack is not released for now.

## Update matrix (everything we ship)

The table below covers all user-facing released assets and how updates work.

| Shipped asset | How you got it | Updates happen when… | Automatic? | How to update / control |
| --- | --- | --- | --- | --- |
| **Desktop app** (Tauri, “Tori” / Happier desktop) | The Windows installer or Linux package from the `ui-desktop-stable` release | The app checks a signed update feed and offers an in-app update | **Checks automatically**, install is **user-triggered** | Accept the in-app update prompt |
| **Self-hosted web UI bundle** (`happier-ui-web`) | Embedded/served by your self-hosted server or Docker image | It changes when your server runtime updates | Depends on the host (see below) | Control updates via the host (`happiest relay host install`, the server installer, or an image rebuild) |
| **Relay server Docker image** (built from the repository `Dockerfile`) | `docker build` from a checkout of the repository; Happiest publishes no image | You rebuild the image from newer source and recreate the container | No | Pull the latest source, rebuild with `docker build`, then recreate the container |
| **UI embedded in relay-server Docker image** | Part of the Docker image build | It updates with the Docker image | No | Same as the Docker image update (rebuild + recreate) |
| **Managed Relay runtime** (`happiest relay host …`) | Install the Happier CLI, then run `happiest relay host install …` | You rerun `happiest relay host install` | No | `happiest relay host install` (local or with `--ssh user@host`) |
| **CLI installer** (`install.sh` / `install.ps1` from the `cli-stable` release) | `curl …install.sh \| bash` / `irm …install.ps1 \| iex` | You rerun it (or use the CLI’s self-update for installer installs) | No | Re-run the installer, or run `happiest self update` |
| **CLI installer payload** | Installed under `~/.happiest/cli/{versions,current,previous}` with a `happiest` shim in `~/.happiest/bin` and `~/.local/bin` (on Windows, `%USERPROFILE%\.happiest\bin`) | You run `happiest self update` or rerun the installer | No (but it can show notices) | Run `happiest self update`. You can pin an exact version with `--to <version>`. |

## Integrity verification (binaries + bundles)

Self-host and relay runtime downloads are verified before install:

- **SHA256**: downloaded archive matches the published checksums file.
- **minisign**: the checksums file is verified with Happiest’s own minisign public key, which ships with the installer.

## Desktop app (Tauri)

The desktop app uses Tauri’s updater plugin:

- it checks an update feed automatically
- it shows an in-app banner/prompt when an update is available
- installing the update downloads a signed bundle and restarts the app

The feed is `https://github.com/ErikaAlk/happiest/releases/download/ui-desktop-stable/latest.json`, so the app updates from the `ui-desktop-stable` release. The Windows installer is not code-signed; Windows can show an unknown-publisher warning when you first run it.

## CLI updates

### Update notices (opt-out)

The CLI can print a periodic “update available” notice in TTY sessions and perform background checks.

The notice includes the command to update:

- `happiest self update`

Disable update checks + notices:

- `HAPPIER_CLI_UPDATE_CHECK=0`

Tune frequency:

- `HAPPIER_CLI_UPDATE_CHECK_INTERVAL_MS`
- `HAPPIER_CLI_UPDATE_NOTIFY_INTERVAL_MS`

### If you installed the CLI via our installer (binary)

Check/update:

```bash
happiest self check
happiest self update
```

Pin to a specific version:

```bash
happiest self update --to 0.1.0
```

`self update` downloads the release and verifies its signature, checks that the new `happiest`
starts on this machine before switching to it, and — when the background service is running —
restarts the service on the new version. If the service does not come back on it, the previous
version is put back and restarted, and the update reports that it was rolled back (or, if even the
previous version does not come back, that it failed). `--to` takes an exact published version. On
Windows, `self update` stops the background service and ends running sessions before it switches
versions, as the installer does.

Rerunning the installer is also a valid update path:

<Tab value="Linux">

</Tab>

## Installers & binaries (what’s automatic vs manual)

Installers and binary installs do **not** auto-update in the background.

What *is* automatic:

- **Update notices** for interactive CLI usage (TTY): `happiest` prints a notice and tells you to run `happiest self update`

What is *manual*:

- actually installing an update (running the update command or rerunning the installer)

### CLI installer (`install.sh`)

The installer supports a few “actions” that are useful for scripting:

```bash
# Check the installed binary + PATH shim
curl -fsSL https://github.com/ErikaAlk/happiest/releases/download/cli-stable/install.sh | bash -s -- --check

# Print the latest version available
curl -fsSL https://github.com/ErikaAlk/happiest/releases/download/cli-stable/install.sh | bash -s -- --version

# Update/reinstall to latest
curl -fsSL https://github.com/ErikaAlk/happiest/releases/download/cli-stable/install.sh | bash
```

Windows (PowerShell) updates work the same way (rerun the installer).

### Managed Relay runtime (`happiest relay host …`)

Install or update your managed Relay runtime by running:

```bash
happiest relay host install --mode system
```

Remote host (over SSH):

```bash
happiest relay host install --ssh user@host --mode system
```

Then manage it with `happiest relay host status` and `happiest relay host start|stop|restart`.

## Server / self-host updates

There are multiple supported self-host shapes. See also: [Self-host runtime](/self-hosting/self-host-runtime).

### Managed Relay runtime (`happiest relay host …`)

Update/reinstall (install-or-update):

```bash
happiest relay host install --mode system
```

Then restart if needed:

```bash
happiest relay host restart --mode system
```

### Server install script

On Linux, the server installer is the same installer with the server product selected. Rerunning it installs the newest `server-stable` release, and a running server keeps using the old version until you restart it:

```bash
curl -fsSL https://github.com/ErikaAlk/happiest/releases/download/cli-stable/install-server.sh | bash
```

On Windows, install and update the server with `happiest relay host install`.

### Relay server Docker image

Happiest publishes no Docker image, so the image you run is one you built from the repository `Dockerfile`. It updates only when you rebuild it and recreate the container. The `server` target builds from the source tree, so pull the latest source first:

```bash
git pull
docker build -t <your-image> --target server .
docker compose up -d --force-recreate
```

The `relay-server` target packages a published server release instead, so rebuild it against the newer release version. The embedded UI updates together with the image. [Docker](/self-hosting/docker) covers the build targets and arguments.
