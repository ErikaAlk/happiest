title: Self-host runtime
description: Understand the supported ways to run a self-hosted Happier Server, and what each option installs/manages.
---

Happier currently supports two **different** self-host “shapes”:

1) a **managed install** (service + config) driven by `happiest relay host …`
2) a **Docker image** that you build from this repository, with a verified server release baked into the image

They are complementary, but they are not the same thing.

For a complete “what updates automatically vs manually” matrix across all shipped assets (desktop/mobile/web, CLI installers, and Docker images), see: [Updates](/releases/updates).

## Option A: Managed self-host install (recommended when you want a service)

Use `happiest relay host install` when you want:

- the server installed as a **managed service** (user/system mode)
- a repeatable **install-or-update** command that always fetches the latest stable release

The relay server is published for Windows x64, Linux x64 and Linux arm64. There is no macOS build.

First, install the Happier CLI: see [CLI install](/apps/cli).

Install locally:

```bash
happiest relay host install --mode system
```

Install remotely over SSH:

```bash
happiest relay host install --ssh user@host --mode system
```

After install, you manage it with:

```bash
happiest relay host status
happiest relay host start
happiest relay host stop
happiest relay host restart
```

A managed server listens on port 3015, on the loopback address unless you pass `--lan`, `--expose` or `--host <ip>` to a local `happiest relay host install`. To update, rerun `happiest relay host install` (it installs or updates to the latest stable release).

### Auth compatibility during this update

Keep `HANDY_MASTER_SECRET` unchanged. Persistent auth tokens and encrypted server data are both derived from it, so rotating it is not an auth-repair procedure and can make existing data unreadable.

## Option B: Docker image

You build the image from the repository `Dockerfile`: its `relay-server` target downloads a signed server release and verifies it during the Docker image build. The running container starts the embedded `happiest-server` binary directly.

This is ideal when:

- you run the server in **Docker**, Compose, Nomad, or Kubernetes
- you want image-based updates that you control
- you do not want the container to download new application artifacts on every restart

Happiest publishes no Docker images, so every update is a rebuild of the image against a newer server release.

See: [Docker](/self-hosting/docker).

## Choosing between them

- If you want a **service** and managed lifecycle → use **Option A**.
- If you want a self-contained container image → use **Option B**.

If you’re unsure, start with the managed install on a plain Linux or Windows host, and use Docker when you already run containers.
